# Writing Style Guide

사용자가 직접 쓴 글 6편(`examples/`)에서 뽑은 규칙이다.
**스터디 글의 구조 + 편하게 쓴 글의 어조**를 섞는 것이 기본 방향이다.

| 출처 | 가져오는 것 |
|---|---|
| `study-*.md` | 번호 붙인 섹션, 대시 불릿, `용어 : 설명` 정의, 코드 안 한국어 주석, 군더더기 없는 밀도 |
| `casual-*.md` | 설명 문단의 합니다체, 단계 순서대로 짚어 주는 진행, 주의사항 괄호 안내 |

## 어조

- **설명 문단은 합니다체**로 쓴다. 독자에게 순서대로 알려 주는 말투다.
  - 예: `그라디언트 툴을 선택했다면 옵션바가 위의 사진처럼 나타나게 되는데요.` → 기술 문서용으로 다듬으면 `도구를 선택하면 옵션바가 나타납니다.`
- **핵심 정리·목록은 개조식(`~함`, `~음`, 명사형)**으로 쓴다. 문장을 길게 늘이지 않는다.
  - 예: `- 라우팅은 예전에는 보통 서버에서 관리하는 로직`
- 한 문단에서 두 방식을 섞지 않는다. 설명 문단 뒤에 정리 목록을 붙이는 구성이다.
- 인사말, 맺음 인사, 이모티콘은 쓰지 않는다 (블로그와 다른 점).

## 문장

- 한 문장에 한 가지만 담는다. 60~80자를 넘으면 끊는다.
- 한 문단은 3문장 이하로 유지한다.
- 독자를 2인칭으로 부르지 않는다. `여러분`, `~해 보세요` 대신 `~하면 됩니다`, `~합니다`를 쓴다.
- 확인하지 못한 내용은 단정하지 않는다. `~라고 합니다`, `~로 보입니다`처럼 출처를 드러낸다.
  - 예: `브러시를 사용할 때에는 새로운 레이어를 생성하는 것을 권장한다고 합니다.`

## 구조

- 섹션 제목은 `## 01. 제목` 형태로 번호를 붙인다. 번호는 두 자리(`01`, `02`)로 맞춘다.
- 각 섹션은 **설명 1~2문단 → 정리 불릿 → (필요하면) 코드**의 순서로 쓴다.
- 정의는 `- 용어 : 설명` 형태로 적는다. 콜론 앞뒤로 공백을 둔다.
  - 예: `- Code Spliting : 기능별로 파일을 분리시켜 필요한 시점에만 파일을 불러오는 전략`
- 하위 항목은 4칸 들여쓰기한 대시 불릿으로 쓴다.
- 비교·분류는 불릿을 나열한다. 항목이 4개를 넘고 축이 2개 이상이면 표를 쓴다.

## 코드

- 코드 블록에는 언어를 표시한다(` ```bash `, ` ```ts `).
- 코드 안 주석은 한국어로, 그 줄이 무엇을 하는지만 짧게 적는다.
  - 예: `// match.params : url 프로퍼티가 들어있음`
- 실행 명령은 복사해서 바로 쓸 수 있는 형태로 적는다.

## 용어

- 영문 고유명사와 기술 용어는 원문 그대로 둔다: `MCP`, `RAG`, `LLM`, `Route`, `props`
- 한글로 굳어진 말은 한글로 쓴다: 라우팅, 렌더링, 파싱, 배포
- 처음 나오는 약어는 `MCP(Model Context Protocol)`처럼 한 번만 풀어 쓴다.
- 단축키·옵션·파일명은 백틱으로 감싼다: `Alt + Delete`, `ignoreQueryPrefix`, `package.json`

## 주의·보충

- 놓치기 쉬운 부분은 문장 뒤 괄호나 별도 줄로 덧붙인다.
  - 예: `(크기를 키워도 보이지 않는다면 CapsLock을 꺼야 합니다.)`
- 참고 링크는 문장 안에 넣지 말고 해당 문단 끝이나 `## 참고 자료` 섹션에 모은다.
